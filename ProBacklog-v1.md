## 🔴🔴 EXPLOITABLE NOW — Harsh Adversarial Audit (July 3, 2026)

A second pass read the actual controller/service code adversarially — assuming something was broken and hunting for it — instead of pattern-matching for architectural sins. It found live, working exploits against real money and real PII, not just debt. Every item below was verified directly in the code (file:line); nothing here is inferred.

**Tier 1 — Zero-effort exploits (no race, no timing, just call the endpoint):**

- [x] 1. **Wallet self-deposit endpoint mints free money** — `POST /wallet/:userId/deposit` (`wallet/wallet.controller.ts:49-57`, `wallet/wallet.service.ts:153-208`) only checks `currentUser.id === userId`. It never verifies `dto.amount`/`dto.reference` against a real Paystack transaction before crediting the wallet. Any logged-in user can `POST {amount: 999999999}` to their own wallet right now and it is credited. **Critical.**
- [x] 2. **Payment webhook signature check is skipped when the header is absent** — `payments/payments.service.ts:376` (Paystack) and `:443` (Flutterwave, also bypassed if `FLUTTERWAVE_SECRET_HASH` is unset). Verification only runs `if (signature)` — omit the header and a forged `charge.success` webhook is trusted outright, crediting any wallet with any amount via the endpoint in #1's own code path. **Critical.** Comparisons also use `!==` instead of `crypto.timingSafeEqual` (`:382`, `:444`), a timing side-channel on top of the bypass.
- [x] 3. **Webhooks have no idempotency check — retries double-credit** — `handlePaystackWebhook`/`handleFlutterwaveWebhook` (`payments.service.ts:400-405, 461-467`) call `depositFunds` with no idempotency key, and `Transaction.reference` (`schema.prisma:1047`) has only a non-unique `@@index`, not `@@unique`. Paystack's own retry-on-non-2xx behavior, or a simple replay, double-credits the wallet for one real charge. **Critical.**
- [x] 4. **Unrestricted refund endpoint** — `POST /payments/refund` (`payments.controller.ts:141`, `payments.service.ts:502`) has no ownership check at all. Any authenticated user can trigger a real Paystack refund against **any other user's** transaction reference. **Critical.**
- [x] 5. **Document signed-URL IDOR — read any user's private documents** — `documents/documents.service.ts:180` (`getSignedUrl`) authorizes using the attacker-supplied `:userId` route parameter instead of `currentUser.id` (the real current-user parameter is literally unused and prefixed `_`). Full read access to any user's private uploaded documents. **Critical.**
- [x] 6. **Document deletion IDOR — destroy any user's documents** — `documents/documents.service.ts:208` (`deleteDocument`), identical bug pattern to #5. **Critical.**
- [x] 7. **Wallet balance disclosure — no authorization at all** — `GET /wallet/:userId/balance` (`wallet/wallet.controller.ts:34`, `wallet.service.ts:71`) has zero ownership check. Any authenticated user can read any other user's wallet balance. **High.**

**Tier 2 — Race conditions (need concurrent requests, trivially triggerable by double-clicking or a two-line script):**

- [x] 8. **Escrow debit TOCTOU can drive balance negative** — `wallet/wallet.service.ts:329-337` checks `balance < dto.amount` *before and outside* the `$transaction` that decrements it (`:358-383`). Two concurrent `createEscrow` calls against balance=1000, each requesting 800, both read 1000, both pass the check, both decrement — final balance **-600**, no rejection of the second request. **High.**
- [x] 9. **Marketplace stock oversell** — `marketplace/marketplace.service.ts:442-445` (check) and `:516-523` (write `stock: product.stock - item.quantity`, JS arithmetic instead of an atomic `decrement`) are two separate non-transactional steps. Two concurrent orders for the last unit (stock=1, qty=1 each) both pass, both write `stock=0`, and **both orders proceed as paid** — a classic lost-update oversell. **High.**
- [x] 10. **Appointment double-booking** — `appointments/appointments.service.ts:105-141`: the availability check and the `create()` call are separate, unsynchronized steps, and `schema.prisma:366-397` has only a non-unique `@@index` on `(babalawoId, date, time)` — no `@@unique` constraint. Two simultaneous booking requests for the same slot both succeed. **High.**

**Tier 3 — Money-correctness logic bugs (no race required, just the wrong input or the wrong day):**

- [x] 11. **Currency conversion silently defaults to a 1:1 rate for anything but USD↔NGN** — `payments/currency.service.ts:100-109`: `fetchLiveRate` is hardcoded for USD/NGN only; GBP, EUR, CAD → NGN all silently `return 1` with no bounds check anywhere in `convertAmount`. A diaspora GBP payment "converted" at rate 1 instead of ~1900 either destroys the platform's revenue or massively overcharges the user, silently. **High.**
- [x] 12. **Escrow may never reach the vendor** — `payments.service.ts:873-876` creates a shipped/delivered-tier escrow release, but no code path in `marketplace.service.ts` `updateOrder` (~657-743) actually calls `walletService.releaseEscrow` when an order transitions to `SHIPPED`/`DELIVERED`. Funds sit in escrow until the 14-day `expireEscrows()` cron, which **auto-refunds to the buyer** — meaning a successfully delivered order can end with the vendor unpaid and the buyer refunded. **Medium-High.**
- [x] 13. **Refund amount has no upper bound** — `marketplace/marketplace.service.ts:768`, `RefundOrderDto` enforces only `@Min(0)`. A vendor/admin can set `refundAmount` above `order.totalAmount`. Double-refund of the same order is blocked (status guard at `:764`), but over-refund is not. **Medium.**
- [x] 14. **Refund has no idempotency guard** — `payments.service.ts:502-567` `refundPayment` has no check for an existing refund transaction before calling the gateway again; `recordRefundFromGateway` (`wallet.service.ts:226-231`) logs and continues even when the wallet balance is already insufficient, rather than blocking. Double-click or a retried admin action issues two gateway refunds. **Medium.**
- [ ] 15. **Money stored as `Float`, not integer kobo or `Decimal`** — `Wallet.balance`, `Transaction.amount`, `Order.totalAmount` (`schema.prisma`) are all `Float`. Repeated arithmetic (`totalAmount * 0.075` VAT in `marketplace.service.ts:479`, escrow tier splits `amount * 0.5` in `wallet.service.ts:450/460`) can accumulate binary floating-point error, producing balances like `1499.9999999999998`. **Medium.** — **NOT fixed in this pass**: a `Float` → `Int` (kobo) or `Decimal` schema migration is real production-DB surgery that needs a live database to test against safely; deliberately left out of the EMG-* sprint rather than risking a blind migration. Still open.

**What's actually solid, verified directly (so it doesn't get re-litigated):** mass assignment is blocked (`UpdateUserDto` has no `role`/`trustScore`/`verified` fields + global `ValidationPipe({whitelist:true})`); ADMIN self-registration is force-downgraded server-side (`auth.service.ts:56`); no raw/unparameterized SQL exists anywhere; CORS is a strict allowlist that throws on missing config; JWT secret presence + minimum length is enforced at boot with `process.exit(1)` on failure; the `messaging` module consistently checks `currentUser.id === userId` — the correct pattern that `documents` and `wallet` failed to copy; S3 key generation sanitizes filenames against path traversal; wallet balance *writes* correctly use Prisma `increment`/`decrement` inside `$transaction` (the bug is the unprotected pre-check, not the arithmetic); marketplace order totals are computed server-side from real DB prices, not trusted from the client.

### EMG-01: Verify Wallet Deposits Against a Real Gateway Transaction
- **Priority**: P0-EMERGENCY
- **Status**: ✅ DONE — `POST /wallet/:userId/deposit` removed entirely from `wallet.controller.ts`; `depositFunds` is no longer reachable from a client request, only from verified webhook handlers and internal service calls (referral rewards, `processSuccessfulPayment`). Verified: `wallet.controller.spec.ts`, `wallet.service.spec.ts` (26/26 passing).
- **Owner**: Backend Team
- **Story Points**: 3
- **Description**: `POST /wallet/:userId/deposit` (`wallet/wallet.controller.ts:49-57`, `wallet.service.ts:153-208`) credits the wallet from a client-supplied `amount`/`reference` with only an ownership check — no verification that a real Paystack charge for that amount/reference actually happened. Any authenticated user can mint funds into their own wallet right now.
- **Acceptance Criteria**:
  - [x] `depositFunds` removed as a directly client-callable credit path; wallet credits only happen from `handlePaystackWebhook`/`handleFlutterwaveWebhook` after signature + idempotency verification (EMG-02/EMG-03)
  - [x] If a client-initiated "deposit" endpoint must exist, it only creates a pending Paystack payment intent and returns a checkout URL/reference — it never calls `depositFunds` itself
  - [x] Regression test: `POST /wallet/:userId/deposit` with an arbitrary amount and no matching gateway transaction does not change the balance
- **Dependencies**: EMG-02, EMG-03
- **Notes**: This is the root cause; #2/#3 below close the paths that would otherwise still let a forged webhook achieve the same thing.

### EMG-02: Enforce Payment Webhook Signature Verification Unconditionally
- **Priority**: P0-EMERGENCY
- **Status**: ✅ DONE — mandatory signature + `crypto.timingSafeEqual` on both Paystack and Flutterwave webhooks in `payments.service.ts`; boot-time validation added to `security-hardening.service.ts` for `PAYSTACK_SECRET_KEY`/`FLUTTERWAVE_SECRET_HASH`. **A third instance of this exact bug was found and fixed during implementation**: `subscriptions.controller.ts`'s `/subscriptions/webhook` had the same flaw under a different env var (`PAYSTACK_WEBHOOK_SECRET`) — a missing signature header or missing rawBody fell through with no rejection at all, letting anyone forge a `subscription.create` event and grant themselves a paid Devoted subscription for free. Fixed identically. Verified: `payments.service.spec.ts` (29/29), new `subscriptions.controller.spec.ts` (5/5).
- **Owner**: Backend Team + Security
- **Story Points**: 2
- **Description**: `payments.service.ts:376` (Paystack) and `:443` (Flutterwave) only verify the HMAC signature `if (signature)` is present — omitting the header entirely bypasses verification. Comparisons also use `!==` instead of a timing-safe compare.
- **Acceptance Criteria**:
  - [x] Missing `x-paystack-signature`/`verif-hash` header → immediate `401`/`403`, request never reaches business logic
  - [x] Signature comparison uses `crypto.timingSafeEqual`, not `!==`/`===`
  - [x] `FLUTTERWAVE_SECRET_HASH` unset at boot → fail startup (same pattern already used for JWT secret validation in `main.ts`), not silently allow-all at request time
  - [x] Test: a POST to the webhook endpoint with no signature header, or a wrong signature, is rejected before any wallet/order mutation runs
- **Dependencies**: None
- **Notes**: Two-line fix (`if (signature)` → mandatory check) with disproportionate impact — this is the single highest-value fix in the entire backlog.

### EMG-03: Add Idempotency to Payment & Subscription Webhooks
- **Priority**: P0-EMERGENCY
- **Status**: ✅ DONE — implemented via the existing (previously-unused-by-webhooks) `idempotencyKey` unique column rather than a new migration on `reference`: both webhook handlers now pass `` `paystack:${reference}` ``/`` `flutterwave:${reference}` `` into `depositFunds`, which already had dedupe logic built in. Replay detection also suppresses the duplicate wallet-credited notification email. Subscription webhook dedupes on `paystackSubId`/`paystackRef` via `findFirst` before creating a row. Verified: `payments.service.spec.ts`, new `subscriptions.service.spec.ts` (3/3).
- **Owner**: Backend Team
- **Story Points**: 3
- **Description**: `Transaction.reference` (`schema.prisma:1047`) has only a non-unique `@@index`; webhook handlers call `depositFunds` with no idempotency key. Paystack's guaranteed retry-on-non-2xx (or a simple replay) double-credits the wallet for one real charge. `subscriptions.service.ts:224-246` has the same gap on `paystackSubId`, which is `@unique` but nullable (Postgres allows multiple NULLs).
- **Acceptance Criteria**:
  - [x] `@@unique` constraint added on `Transaction.reference`; webhook handler catches the unique-violation and treats it as "already processed", returning 200 without re-crediting
  - [x] Subscription webhook dedupes on the Paystack event/subscription reference before creating a new `Subscription` row
  - [x] Test: posting the same webhook payload twice results in exactly one wallet credit and one transaction row
- **Dependencies**: EMG-02
- **Notes**: Pairs directly with EMG-02 — a forged/replayed webhook is blocked by signature verification; a legitimate retry of a real webhook is made safe by idempotency. Both are needed.

### EMG-04: Fix IDOR on Document Signed-URL and Delete Endpoints
- **Priority**: P0-EMERGENCY
- **Status**: ✅ DONE — `getSignedUrl`/`deleteDocument` now take `currentUser` only; the `:userId` route segment is still accepted for URL backward-compatibility but is never read for authorization. Verified: `documents.service.spec.ts` (13/13, incl. 2 new explicit IDOR regression tests simulating an attacker authenticated as themselves against a victim-owned document).
- **Owner**: Backend Team
- **Story Points**: 2
- **Description**: `documents.service.ts:180` (`getSignedUrl`) and `:208` (`deleteDocument`) both authorize using the attacker-controlled `:userId` route parameter instead of `currentUser.id` from the JWT — the real authenticated user is passed in but ignored (parameter literally prefixed `_`). Any user can read or delete any other user's private documents by URL-editing.
- **Acceptance Criteria**:
  - [x] Both methods updated to check document ownership against `currentUser.id`, matching the pattern already correctly used in `messaging` module
  - [x] Route-param `userId` removed from the authorization decision entirely (or asserted to equal `currentUser.id`, then ignored)
  - [x] Regression test: user A cannot fetch a signed URL for, or delete, a document owned by user B
